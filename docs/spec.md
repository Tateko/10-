## 0. 一文で

**michi は、「あなたが自分では選ばない体験」を、選ばない理由・誘う相手・最初の一歩まで揃えて、今日この後の予定として差し出す秘書である。**

レコメンドは「あなたが好きそうなもの」を出して世界を狭める。michi は逆を行く。傾向の外側にあり、それでも今日実行できる行動だけを出す。

---

## 1. なぜ作るか

### 1.1 前提としている10年後（2036年）

- AIとロボットで「効率化できること」は効率化され尽くしている。
- 稼ぐ・調べる・手配する、といった**手段の仕事はAIが代替**する。お金の相対的な価値は下がる。
- すると人間の物差しは **感情と経験** に移る。ブランド品を買った幸福は一時的だったが、「北海道で美味いものを食べたい」という感情は行動の起点になり続ける。
- 全てが効率化された世界では、**あえて非効率なこと**（人と会う、実店舗で悩む、予想外に出会う）に価値が戻る。

### 1.2 残る課題

- 自分で気づいていることは、もうAIがやってくれる。**価値が残るのは「気づいていないことを気づかせる」こと。** 歯科医が患者の口の中を見て初めて歯並びの問題が分かるように、自分の傾向は自分では見えない。
- 既存のレコメンド・検索は「過去の自分」を強化する。休日はいつも同じカフェ、人と会うのは月1回、という人に、同じカフェを勧め続ける。
- 判断すること自体が疲れる。「今日何をするか」を毎回ゼロから考えたくない。判断コストが残る限り、人はいつもの行動に戻る。

### 1.3 michi の答え

1. **傾向を推定する** — ユーザーの記述（いつもの過ごし方、気分、同行者）から「この人が選ばないもの」を言葉にする。
2. **外側を生成する** — 傾向の外側にあり、今日・この時間・この予算で実行できる行動を作る。
3. **行動に落とす** — 誘う相手・そのまま送れる誘い文・60秒でできる最初の一歩を付け、判断ゼロで動けるようにする。

感情が一番動くのは「人が絡むとき」なので、3案のうち少なくとも1つは必ず人を誘う設計にする。

## 2. 対象ユーザーと利用シーン

### 2.1 ペルソナ

| | A: 判断疲れの会社員 | B: 世界が狭くなっている一人暮らし | C: 誰かを誘いたいが口実がない人 |
|---|---|---|---|
| 状況 | 平日は仕事。休日は動画とサブスクで終わる。外出先は決まった数店 | 引っ越し・転職で交友範囲が縮小。休日に予定が無い | 会いたい友人はいるが「用事がない」と誘えない |
| 痛み | 何かしたい気持ちはあるが、探す・決めるのが面倒 | 検索しても「行きそうな場所」しか出てこない | 誘う理由と文面を考えるのが億劫 |
| michi が出す価値 | 3案から選ぶだけ。決めたら「最初の一歩」をやる | 「自分では選ばない理由」が刺さり、外に出る | 誘い文がそのまま使える。提案自体が口実になる |

### 2.2 利用シーン（時間軸）

- **平日夜 18:30、駅で** — 「使える時間 1時間半・疲れている」→ 帰宅と真逆の一手を出す。
- **土曜 11:00、家で** — 「半日・暇でだるい・同期のA」→ 誘い文をコピーしてそのまま送る。
- **出張先の空き時間** — 知らない街を「〜のような場所で〜する」形で提案。固有名詞の断定はしない。

### 2.3 非対象（今は）

- 旅行の行程作成、レストラン予約、購買の自動化（Claude Code や既存サービスで代替可能。差別化にならない）。
- 匂い・味のデジタル化（技術的に未成熟。アイデア出しで出たが今回は外す）。

## 3. コンセプトの核（設計原則）

| # | 原則 | 具体 |
|---|---|---|
| P1 | **選ばない理由を必ず言う** | すべての提案に `why_you_wouldnt_pick` を付ける。根拠はユーザーの入力から引く。理由が書けない案は出さない |
| P2 | **無難・定番・効率的な案は出さない** | 「駅前のカフェでゆっくり」のような案は禁止。既存レコメンドの領域に入らない |
| P3 | **今日実行できる** | 使える時間・予算・エリアの制約内。「いつかやる」案は出さない |
| P4 | **人が絡む** | 3案のうち1案以上は人を誘う。誘い文は50〜80文字、そのまま送れる文体 |
| P5 | **でっち上げない** | 存在を確認できない店名・施設名は出さない。「〜のような場所」と書き、場所の確定はユーザー側 |
| P6 | **判断コストを削る** | 出力は「選ぶ」「コピーする」「一歩やる」の3操作で完結。説教・長文・選択肢の羅列をしない |
| P7 | **止まらない** | APIキー・ネットワークが無くても固定の3案で動く（モック）。デモも日常利用も止まらない |

## 4. 機能仕様

### 4.1 スコープ

| レベル | 内容 | 状態 |
|---|---|---|
| **MVP（今日提出）** | 入力フォーム → 3案生成 → 選ぶ／誘い文コピー。モックフォールバック | 実装済み |
| **v1（〜1ヶ月）** | 履歴保存、「やった／やらなかった」フィードバック、傾向の蓄積、通知 | 未 |
| **v2（〜半年）** | カレンダー・位置情報連携で入力ゼロ化、地図APIで場所の実在確認、誘った相手側の受け取りUI | 未 |
| **v3（構想）** | 「同じ未知を選んだ人」同士のマッチング、オフラインイベント化、法人向け（福利厚生・チームビルディング） | 未 |

### 4.2 MVP 機能一覧

| ID | 機能 | 説明 | 受け入れ条件 |
|---|---|---|---|
| F-01 | 状況入力 | エリア、使える時間、気分、予算感、最近やったこと・いつもの過ごし方、一緒に動ける人（任意） | エリアのみ必須。他は未入力でも生成できる |
| F-02 | 3案生成 | 入力から `one_liner` と 3つの `proposal` を生成 | 常にちょうど3案。スキーマ違反は返さない（構造化出力） |
| F-03 | 選ばない理由の表示 | 各案に `why_you_wouldnt_pick` をカード上部に強調表示 | 入力文からの引用・言い換えが含まれる |
| F-04 | 誘い文コピー | `invite_message` をクリップボードへ。失敗時は prompt で表示 | 50〜80文字、絵文字なし |
| F-05 | これにする | 1案を選択状態にし、「最初の一歩をやるだけ」と促す | 選択は1つだけ。他案の選択は解除 |
| F-06 | 入力の記憶 | 直前の入力を localStorage に保存し、再訪時に復元 | 保存不可環境でも動作に影響しない |
| F-07 | モックモード | 認証情報なし、または `MOCK=1` のとき固定3案を返す | UI上に「（モック表示）」と明示 |
| F-08 | エラー表示 | 認証・レート制限・API・拒否をそれぞれ日本語で表示 | 白画面・無反応にならない |

### 4.3 v1 で追加する機能（設計済み・未実装）

| ID | 機能 | 説明 |
|---|---|---|
| F-11 | 履歴 | 生成した案と選択結果をユーザー単位で保存 |
| F-12 | 結果フィードバック | 「やった／やらなかった／途中でやめた」＋一言。次回の傾向推定に使う |
| F-13 | 傾向プロファイル | 入力とフィードバックから「この人が選ばない領域」を継続的に更新。プロンプトに注入 |
| F-14 | 通知 | 曜日・時間帯・空き時間を学習し「今日の未知」を1件だけプッシュ。**通知の中身は提案そのもの**（開かせるための通知ではなく、開く理由がある通知） |
| F-15 | 誘い先リンク | 誘い文に michi のリンクを含め、相手が「行く／行かない」を返せる |
| F-16 | 再生成 | 「この方向は違う」と1案だけ差し替える。差し替え理由は傾向に反映 |

## 5. UX仕様

### 5.1 コアループ

```
[状況を入れる] → [3案を読む] → [1案を選ぶ] → [誘い文を送る] → [最初の一歩をやる] → (v1) [結果を返す] → 傾向が更新される → 次回はもっと外側へ
```

ループの評価軸は「読んだか」ではなく **「動いたか」**。KPI は §9 参照。

### 5.2 画面構成（MVP：スマホ1画面＋下部4タブ）

手描きスケッチ（2036/9/12 の画面）に合わせる。**日付 → Hello! → 大きな1枚カード → 下部4タブ**。

```
┌──────────────────────────────┐
│ 2036/9/12                     │  日付
│ Hello, たて!                  │  挨拶（設定の呼び名）
│ 今日、自分では選ばない一手を。   │
│ ┌──────────────────────────┐ │
│ │ 今日の未知 ・ 今日のひとこと  │ │  大きな1枚カード（吹き出し枠）
│ │ 知らない駅で降りて昼を決める  │ │  提案が無いときは最小入力
│ │ 60分 ・ 〜1,500円 ・ 場所ヒント│ │  （エリア／時間／気分）に変わる
│ │ ▍なぜ自分では選ばないか: …   │ │
│ │ やること / 誰を誘う / 最初の一歩│ │
│ │ [これにする] [別の案] [もう一度]│ │  選択後: [誘い文をコピー] [やめる]
│ │           ● ○ ○             │ │  3案のうち何番目か
│ └──────────────────────────┘ │
│                               │
│ [ ! ]   [ 🏠 ]   [ 👤 ]   [ ⚙ ] │  下部タブ
└──────────────────────────────┘
   │        │        │        └ 設定: 呼び名・いつもの過ごし方・予算・よくいるエリア
   │        │        └ 友達: 「友だち100人」リスト。名前タップで「今日誘う人」→提案に反映。
   │        │                「会った」で最後に会った日を更新（リアルに会った人だけ数える）
   │        └ ホーム: 上図
   └ アナタへのオススメ: 3案の一覧（カテゴリ・感情つき）。新着があると赤点
```

| タブ | 役割 | 保存 |
|---|---|---|
| ホーム | 今日の1案に集中させる。判断は「これにする」か「別の案」だけ | 直近の提案と選択（localStorage） |
| アナタへのオススメ | 3案を並べて比較。ここからも「これにする」できる | 同上 |
| 友達 | 誘う相手の台帳。今日誘う人を1人選ぶと `companion` として送られる。未選択なら友達リスト全体をヒントとして送る | 友達配列（localStorage） |
| 設定 | 傾向の根拠になる「いつもの過ごし方」と既定値。生成モード（ライブ／モック）の表示 | 設定オブジェクト（localStorage） |

### 5.3 文体・トーン

- 短く、断定的に、動きたくなる文。説教・前置き・「いかがでしょうか」を書かない。
- 「なぜ自分では選ばないか」は**ユーザー本人の言葉を引用**して書く（例:「休日はだいたい家で動画」と書いているので…）。
- 誘い文は友人に送る口語。絵文字なし。相手が返事しやすいように「来ない？」「やってみない？」で終える。

### 5.4 状態遷移

| 状態 | 表示 | 遷移 |
|---|---|---|
| 初期 | フォームのみ。前回入力があれば復元 | 送信 → 生成中 |
| 生成中 | ボタン無効化、「あなたが選ばない選択肢を探しています…」 | 成功 → 結果 ／ 失敗 → エラー |
| 結果 | one_liner + 3カード | これにする → 選択済み ／ 再送信 → 生成中 |
| 選択済み | 選んだカードに枠線、「決めた。あとは『最初の一歩』をやるだけ。」 | 別カード選択 → 選択済み（切替） |
| エラー | 赤字で理由。フォームは残す | 再送信 → 生成中 |
| モック | 結果と同じ。ステータスに「（モック表示：APIキー未設定）」 | — |

### 5.5 アクセシビリティ・端末

- スマホ幅（〜400px）で1列に崩れる。横スクロールしない。
- フォーム要素はすべて `label` で結び付ける。ボタンはキーボード操作可。
- 色だけで状態を伝えない（選択はテキストも変える）。

## 6. AI設計

### 6.1 モデルと呼び出し

| 項目 | 値 | 理由 |
|---|---|---|
| モデル | `claude-opus-5` | 傾向推定と「外側の生成」は推論の質が結果に直結する |
| 思考 | 既定（adaptive） | 明示設定は不要 |
| effort | `low`（MVP） | デモの体感速度優先。質が足りなければ `medium` |
| 出力形式 | 構造化出力（Zod スキーマ → `output_config.format`） | 毎回ちょうど3案・同じ形を保証し、UIを壊さない |
| max_tokens | 4000 | 3案で十分。ストリーミング不要 |
| フォールバック | なし（意図的） | 拒否時は 422 を返す。デモ中の想定外の 400 を避けるため。v1 で再検討 |

### 6.2 プロンプトの構造

**System（固定）** — キャッシュ効率のため固定文。役割と「守ること」を列挙:

1. 3案とも入力から「選ばない」根拠を持つこと。効率的・無難・いつも通りの案を出さない。
2. 定番スポット紹介ではなく行動の提案。「〜のような場所で、〜をする」。
3. 1案以上は人を誘う要素を必ず含める。
4. 時間・予算・エリアの制約を守る。時間内に終わる。
5. 断定できない固有名詞を出さない。存在しない店・施設をでっち上げない。
6. 説教しない。短く具体的に。日本語。

**User（可変）** — 入力を箇条書きで渡す。現在時刻（JST）を含める（夜に昼の提案をしないため）。

### 6.3 出力スキーマ

```ts
Proposals = {
  one_liner: string            // 30文字以内。今日のこの人への一言
  proposals: Proposal[3]       // ちょうど3件
}
Proposal = {
  title: string                // 15文字前後
  category: "食" | "移動・散歩" | "人と会う" | "文化・鑑賞" | "身体を動かす" | "学び" | "その他"
  why_you_wouldnt_pick: string // 入力を根拠に「なぜ選ばないか」
  what: string                 // 何をするか。2〜3文
  where_hint: string           // 「〜のような場所」。固有名詞の断定なし
  duration_min: number         // 所要分
  cost_hint: string            // 費用感
  invite_who: string           // 誰を誘うか
  invite_message: string       // 50〜80文字、絵文字なし、そのまま送れる
  first_step: string           // 60秒以内にできる最初の一歩
  emotion: string              // 動く感情を一言
}
```

### 6.4 品質基準（生成物の合格ライン）

| 観点 | 合格 | 不合格例 |
|---|---|---|
| 外側性 | 入力の傾向と明確に違う | 「近くのカフェで読書」（傾向の内側） |
| 根拠 | 入力の言葉を引いている | 「あなたは外出が少なそうなので」（推測のみ） |
| 実行可能性 | 時間・予算内、今からできる | 「週末に日帰り旅行」（今日60分の入力に対して） |
| 人 | 3案中1案以上に誘う要素 | 3案とも一人で完結 |
| 事実性 | 固有名詞は「〜のような」 | 「渋谷の○○カフェで」（実在未確認） |
| 文体 | 短く動詞で終わる | 「〜してみるのはいかがでしょうか」 |

v1 ではこの表を **LLM-as-judge の評価セット**にし、プロンプト変更ごとに回帰させる。

### 6.5 v1 以降のAI拡張

- **傾向プロファイル注入**: フィードバック履歴から「選ばない領域」「実際に動いた領域」を要約し、System の後・User の前に差し込む（キャッシュされた固定部分を壊さない）。
- **場所の実在確認**: 地図APIで `where_hint` を実在の候補に解決。解決できなければヒントのまま。
- **通知文生成**: 提案1件を通知1行に圧縮する専用プロンプト。

## 7. システム構成

### 7.1 MVP

```
ブラウザ (public/index.html, 依存なし)
   │  fetch POST /api/suggest
   ▼
Express (server.js, Node 22, ESM)
   ├─ 認証情報あり → Anthropic SDK → claude-opus-5（構造化出力）
   └─ なし / MOCK=1 → 固定3案（mockProposals）
```

- 状態はサーバーに持たない。入力の記憶はブラウザの localStorage のみ。
- 環境変数: `ANTHROPIC_API_KEY`（または `ant auth login` のプロファイル）、`MOCK`、`PORT`。

### 7.2 API

#### `POST /api/suggest`

リクエスト（すべて文字列、`area` 以外は省略可）:

```json
{ "area": "渋谷", "minutes": "60", "mood": "何か刺激がほしい",
  "budget": "〜1,000円", "recent": "休日はだいたい家で動画", "companion": "同期のA" }
```

レスポンス `200`: `{ "mode": "live" | "mock", "one_liner": string, "proposals": Proposal[3] }`

| コード | 意味 | 表示文 |
|---|---|---|
| 422 | モデルが生成を拒否 | 提案を生成できませんでした。入力を変えて試してください。 |
| 429 | レート制限 | 混雑しています。少し待ってから再実行してください。 |
| 500 | 認証エラー／サーバー内部 | APIキーが無効です／サーバーエラー: … |
| 502 | API エラー・形式不正 | API error {status} ／ 応答の形式が不正でした。 |

#### `GET /api/health` → `{ "ok": true, "mode": "live" | "mock", "model": "claude-opus-5" }`

### 7.3 v1 構成（案）

- 認証: メールリンクまたは OAuth。ユーザーIDに履歴・傾向を紐づける。
- 保存: 履歴・フィードバック・傾向要約（SQLite → Postgres）。
- 通知: Web Push（PWA）から始め、LINE 連携へ。
- 誘い先リンク: `/i/:token` で相手が「行く／行かない」を返す。相手はアカウント不要。

## 8. 非機能要件

| 項目 | MVP | v1 |
|---|---|---|
| 応答時間 | 生成 15秒以内を目標（effort low） | 8秒以内。超える場合は段階表示 |
| 可用性 | API不通でもモックで動く | 同左＋直近の提案をキャッシュ表示 |
| セキュリティ | APIキーはサーバー側のみ。リクエストボディ 64KB 上限 | 認証、レート制限、入力のサニタイズ |
| プライバシー | サーバーに保存しない | 履歴は本人のみ閲覧。削除機能。第三者提供なし |
| コスト | 1回あたり数円（低effort・短出力） | System 固定化でキャッシュ利用 |
| ログ | エラーのみ標準出力 | 生成品質の追跡のため入力ハッシュと結果を保存 |

## 9. 成功指標

| 段階 | 指標 | 目標 |
|---|---|---|
| ハッカソン | 5観点の合計点 | 実現性・新規性で 5、価値・AI・展開性で 4 以上 |
| v1 | **行動率** = 「やった」/ 生成回数 | 20% |
| v1 | 誘い文送信率 | 30% |
| v1 | 誘われた側の「行く」返答率 | 40% |
| v1 | 7日継続率 | 25% |
| 定性 | 「自分では選ばなかった」と本人が言うか | ユーザーインタビューで確認 |

「開いたか」「読んだか」は KPI にしない。**動いたか、人と会ったか**だけを見る。

## 10. 審査5観点との対応

| 観点 | michi の答え |
|---|---|
| 価値 | 判断疲れ・世界の縮小・誘う口実の欠如、という3つの痛みを1画面で解く。AIが判断を代替する世界で残る「気づかせる」価値 |
| 実現性 | 動く。構造化出力で毎回同じ形。認証なしでもモックで止まらない |
| 新規性 | レコメンドの目的関数を反転。「好きそうなもの」ではなく「選ばないもの＋その根拠」 |
| AIの活かし方 | 傾向推定 → 外側生成 → 行動化（誘い文・一歩）の3段。制約プロンプトと事実性ルール |
| 展開性 | 入力ゼロ化（ログ・カレンダー）→ 提案の先に人（誘い先リンク・マッチング）→ 通知の再定義（開く理由がある通知） |

## 11. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 提案が無難になる | 新規性が消える | System の禁止例を増やす。§6.4 の評価セットで回帰 |
| 実在しない店を出す | 信頼を失う | 固有名詞の断定禁止。v2 で地図API照合 |
| 「AIチャットで済む」と言われる | アプリの存在意義 | 通知の先に人がいる設計、履歴からの傾向更新はチャットでは成立しない |
| 危険・迷惑な提案 | 安全性 | System で違法・危険・他者に迷惑をかける行為を禁止。拒否時は 422 |
| デモ中の API 障害 | 実現性の減点 | モックへ即切替。`/api/health` で事前確認 |
| 誘われた相手に負担 | 人間関係 | 誘い文は断りやすい文末に。v1 で「行かない」も一タップ |

## 12. 今後の論点（未決）

1. 名称: 「michi（未知）」で行くか。「道」との二重の意味は狙い通りだが、検索性が低い。
2. 収益: 「お金の価値が下がる世界」の前提と、開発費の現実をどう繋ぐか。案: 提案先の体験提供者（個人店・イベント主催）からの掲載料ではなく、**行動が成立したときだけ**の成果報酬。広告の矛盾（払う側と流す側の両方にコスト）を再現しない。
3. 対象領域の優先順位: 「人と会う」を主軸に据えるか、「移動・散歩」から入るか。行動率で決める。
4. 通知の頻度: 1日1件を上限とするか。多いと「開かない通知」に戻る。
